# E-Commerce Platform Constitution

<!-- TODO(PROJECT_NAME): replace "E-Commerce Platform" with the platform's official commercial name. -->

This document defines the project's non-negotiable principles. Every spec, plan, task, and line
of code — written by a human or generated by an AI agent — MUST comply. Where a request conflicts
with this constitution, the constitution wins; doing otherwise requires amending the constitution
first (see Governance).

## Core Principles

### I. Bounded Context Boundaries & Modular Monolith

The system MUST be divided into clearly delineated bounded contexts, each one an independent
module: `catalog`, `inventory`, `cart`, `order`, `payment`, `pricing/promotion`, `user/identity`,
`shipping/fulfillment`, `review`, `notification`, `search`.

- The starting architecture MUST be a **modular monolith**. Each module owns its internal API and
  MUST NOT read or write another module's database tables or schema directly — all cross-module
  access goes through the owning module's internal API.
- Extracting a module into a microservice is permitted ONLY when there is measured evidence of a
  genuine need to scale it independently (for example `search`, `payment`). That evidence MUST be
  recorded in the plan before extraction begins.
- Synchronous internal API calls are reserved for business operations that need an immediate
  response (inventory checks, price calculation). Work that does not need an immediate response
  (confirmation emails, analytics updates, search index synchronization) MUST go through an
  event/message queue.
- Every significant state change (order placed, payment made, order status changed) MUST emit a
  **domain event** for other modules to subscribe to. Polling another module to detect state
  changes is NOT permitted.

*Rationale*: data boundaries are the most expensive thing to fix later. Keeping them clean from
the start makes service extraction possible without a rewrite.

### II. Data Integrity & Idempotency (NON-NEGOTIABLE)

- The core of order placement and payment (creating the order, decrementing inventory, writing the
  payment record) MUST execute inside a single database-level ACID transaction. Eventual
  consistency is NOT acceptable for these operations.
- Every write API touching money or inventory (placing an order, paying, refunding, decrementing
  stock) MUST be idempotent: it accepts an `Idempotency-Key` header and handles duplicate requests
  safely — no duplicate orders, no double charges.
- Inventory decrements MUST use optimistic locking or a row-level lock to prevent overselling under
  concurrent requests.
- Order data, payment transactions, and inventory history MUST NOT be hard-deleted. Use soft delete
  or status fields, backed by a complete audit trail: who, when, what changed, from which value to
  which value.

*Rationale*: errors in money and inventory do not heal themselves, and every one of them is a real
customer losing money or an order that cannot be fulfilled.

### III. Security & Compliance by Default (NON-NEGOTIABLE)

- Card data (PAN, CVV) MUST NOT be stored anywhere in the system. Payments MUST go through a
  PCI-DSS compliant third-party gateway (VNPay, Momo, ZaloPay, Stripe, ...) using tokenization.
- All customer PII (name, phone number, address, email) MUST be encrypted at rest and in transit.
  TLS is mandatory; plain HTTP endpoints MUST NOT exist.
- Authentication MUST follow OAuth2/OIDC, or JWT with refresh tokens, with rate limiting to defeat
  login brute-forcing.
- Authorization MUST be enforced server-side on every endpoint, by role (customer, seller, admin,
  support). Hiding UI elements does NOT count as an authorization control.
- OWASP Top 10 is the floor: parameterized queries or an ORM against SQL injection, XSS and CSRF
  protection, server-side input validation. No data from the client may be trusted — product
  prices and order totals MUST always be recalculated on the server.
- The system MUST comply with the personal data protection regulations of each market it operates
  in (Decree 13/2023 in Vietnam; GDPR where EU customers are served).

*Rationale*: a single data breach or payment fraud incident costs more than the entire prevention
budget, and most requirements here are legal obligations rather than engineering preferences.

### IV. API Contract Discipline

- REST APIs MUST be resource-based, with versioning in the URL (`/api/v1/...`).
- Every error response MUST follow one consistent format containing an error code, a message, and
  a request id for tracing.
- Every endpoint returning a collection (catalog, orders, reviews, ...) MUST paginate. Returning
  an entire dataset is NOT permitted.
- Inbound webhooks (payment gateways, shipping partners) MUST have their signature verified before
  any part of the payload is processed.

*Rationale*: the API contract is the surface both clients and partners depend on; inconsistent
error formats and unpaginated endpoints leak upward into operational failures at every layer above.

### V. Test-First for Money & Inventory Paths (NON-NEGOTIABLE)

- TDD is mandatory for core business logic: pricing, cart, checkout, payment, inventory. Tests are
  written first, MUST fail first, and only then is the implementation written.
- Minimum test coverage: **90%** for money and inventory modules, **80%** for all other modules.
  Coverage below the threshold fails the pipeline; it is not a warning.
- Contract testing between modules/services is mandatory, so that breaking changes surface in CI
  rather than in production.
- Load testing is mandatory ahead of every major event (flash sale, Black Friday). The results MUST
  establish the load ceiling and a scaling plan before the event.
- Every PR containing new business logic MUST ship with corresponding tests. Business logic without
  tests MUST NOT be merged.

*Rationale*: payment-path bugs typically appear only under load or in race conditions — the two
things that only test-first design and load testing catch.

### VI. End-to-End Observability

- Every service MUST emit structured logs (JSON) carrying a `request_id`/`trace_id` end to end,
  sufficient to trace a single flow from start to finish: order placed → paid → stock decremented
  → email sent.
- Required metrics: checkout error rate, payment processing time, oversell rate, cart abandonment
  rate.
- Automated alerting MUST fire when: the payment error rate crosses its threshold, API latency
  breaches the SLA, or the event queue backs up.
- Every service MUST expose a health check endpoint usable by the load balancer and the
  orchestrator (k8s liveness/readiness).

*Rationale*: what is not measured cannot be operated; a failed order must be traceable to the exact
step that broke within minutes, not hours.

### VII. Fault Tolerance & Controlled Degradation

- Target SLA: **99.9% uptime for the checkout flow**.
- Every call to an external service (payment gateway, shipping, SMS/email provider) MUST sit behind
  a circuit breaker. One external service going down MUST NOT take the whole system with it.
- Asynchronous operations (sending email, syncing data) MUST retry with exponential backoff.
  Operations that charge or move money MUST NOT be retried automatically without an idempotency
  check first.
- A graceful degradation plan is required: if `search` goes down, the storefront still supports
  browsing by category; if `recommendation` goes down, the page still renders without suggestions
  rather than failing blank.
- Disaster recovery is required: scheduled database backups, a rehearsed recovery runbook, and
  RPO/RTO defined as concrete numbers.

*Rationale*: checkout downtime is revenue lost directly, and partial degradation always beats total
failure.

## Performance, Scalability & User Experience Standards

**Performance & scalability**

- Read-heavy, write-light data (catalog, category tree, product detail) MUST be cached, with an
  invalidation mechanism triggered when a product or price changes.
- The database MUST carry complete indexes for the main business queries: product search, and order
  history by user.
- Every service MUST be stateless so it can scale horizontally. Sessions live in an external store
  (Redis or equivalent); state MUST NOT be held in instance memory.
- Static assets and product images MUST be served through a CDN.

**User experience & accessibility**

- The storefront MUST meet WCAG 2.1 AA at minimum.
- The interface MUST be responsive and mobile-first, because the majority of e-commerce traffic
  arrives from mobile.
- Load time target for the home page and product pages: **LCP < 2s**.

## Development Workflow & Quality Gates

- CI/CD is mandatory. Every merge into the main branch MUST pass the automated test pipeline before
  deployment.
- Changes affecting checkout or payment MUST be deployed using a blue-green or canary strategy.
- Risky new features MUST sit behind a feature flag, so they can be switched off quickly without a
  code rollback.
- Deploying straight to production while bypassing staging/UAT is NOT permitted.

## Governance

**Authority**: This constitution supersedes every other project convention, habit, and document.
Where a spec, plan, task, or code review conflicts with it, the constitution wins.

**Amendment procedure**:

1. A proposed amendment MUST take the form of a PR editing this file, stating which clause changes
   and why.
2. Amendments touching a NON-NEGOTIABLE principle (II, III, V) MUST include a migration plan, with
   a concrete deadline, for existing code that violates the new rule.
3. An amendment takes effect when its PR is approved and merged; the merge date becomes
   `Last Amended`.

**Versioning policy** (semantic versioning applied to this document):

- **MAJOR**: a principle is removed or redefined in a backward-incompatible way.
- **MINOR**: a new principle or section is added, or existing guidance is materially expanded.
- **PATCH**: wording clarifications, typo fixes, translations, and other non-semantic refinements.

**Compliance review**:

- Every PR review MUST confirm the change does not violate this constitution. A reviewer may block
  a merge on a constitutional violation alone.
- Every `/speckit-plan` MUST include a Constitution Check before design work begins.
- Complexity beyond what a principle requires MUST be justified in writing inside the plan; what
  cannot be justified MUST be simplified.
- Runtime development guidance for agents lives in the repository's guidance file (`CLAUDE.md` or
  equivalent); that file MUST NOT contradict this constitution.
